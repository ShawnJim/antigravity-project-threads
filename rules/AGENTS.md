# Project Threads Coordination & Worktree Isolation Rules

1. **Persistent Coordinator Discipline**:
   - If a conversation is titled `[Coordinator] ...` or has been bound via `init_project_coordinator`, remain in Coordinator mode on **every** subsequent user message even when `/coord` is omitted.
   - In a Coordinator conversation, **never** call `invoke_subagent` (`research` / `self`) or `run_workflow` for codebase investigations or edits; always call `project-threads_coordinator` -> `dispatch_thread` (`createWorktree: false` for read-only checks/investigations, `createWorktree: false` + `threadType: "review"` with omitted `model` for code reviews / cross-reviews so the user's Review default model applies, and `createWorktree: true` for code changes) so every task creates a tracked `thr-xxx` thread in the `Project Threads` panel.
   - When dispatching a Worker Thread via `dispatch_thread`, always write `title` and `taskPrompt` in the user's active conversation language (e.g., Chinese when the user speaks Chinese, English when the user speaks English) and instruct the Worker Thread to write its analysis and final summary in that same language.
   - **Archiving Policy**: Once a Worker Thread has completed and been reported:
     - For **read-only investigation / check threads (`createWorktree: false`)**, the Coordinator may **autonomously decide** to call `archive_thread` directly after reporting results without asking the user each time.
     - For **feature development / code-change Worktree threads (`createWorktree: true`)**, do **NOT** auto-archive before user acceptance (even after changes are merged into a branch, keep the thread open for verification or follow-up iterations); however, **once the user confirms acceptance / sign-off** (e.g. "looks good", "ok", "accepted" / "ok了", "没问题", "验收通过") or explicitly requests archiving, **automatically call `archive_thread` directly** without waiting for a separate "archive" command.
   - **Single-Thread Scope Isolation**: Always pass `coordinatorId` and `workspacePath` when calling `list_threads`, `get_thread_detail`, `send_thread_message`, or `archive_thread` so fail-closed cross-project isolation and project-local `#N` lookup are enforced (unscoped single-thread MCP calls are rejected fail-closed).
   - **Two-Tier Shared Project Memory (`update_project_memory`)**: Keep `.agents/rules/project-memory.md` as a concise thin index (`<= 60` lines / `~4KB`) and place module-specific details into on-demand `.agents/memory/<topic>.md` topic files via `update_project_memory(topic="...", ...)`. When conventions change or memory grows, run `mode="read"` first and consolidate/deduplicate with `mode="replace"` or split into topic files rather than endlessly appending.
   - **Pending Decisions Board (`manage_decisions`)**: Not limited to Worker Thread callbacks — whenever the Coordinator asks the user to make ANY call or answer a binary/multi-choice/confirmation question (including everyday planning discussions, architecture/design trade-offs, whether to file an Issue first vs. implement directly, scheduling, branch merge, release, or cleanup), synchronously register it via `manage_decisions(action="add", ...)` with 1–3 quick-action options so it appears in the right-hand **Pending Decisions** section (users may also send custom instructions from any card); when the user decides directly in chat, promptly call `manage_decisions(action="resolve", decisionId="...")` to clear it from the board.

2. **Worker Thread Worktree Isolation**:
   - Whenever a conversation's prompt or `.agents/rules/worker-thread-context.md` assigns an **Isolated Worktree Path** (under `.worktrees/<repo>/<thread>`), perform ALL file reads, edits, writes, and shell commands strictly inside that worktree directory (including reading any recommended `.agents/memory/<topic>.md` topic files on demand from within that worktree). Never modify files in the main repository checkout.
   - Write your analysis and conclude completed Worker Thread assignments in the same language as the task instructions with a `### Thread Summary` (or `### 线程总结`) section summarizing root cause / findings / changes made, modified files or commit hash, and any reusable architectural notes for Shared Project Memory.
